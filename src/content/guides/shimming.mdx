`webpack` 컴파일러는 ES2015 모듈, CommonJS 또는 AMD로 작성된 모듈을 이해할 수 있습니다. 그러나 일부 써드 파티 라이브러리는 전역 종속성을 필요로 할 수 있습니다. (예: `jQuery`의 경우 `$`) 라이브러리는 내보낼 필요가 있는 전역 변수를 만들 수도 있습니다. 이러한 "깨진 모듈은" _shimming이_ 작동하는 하나의 인스턴스입니다.

W> **전역 변수를 사용하지 않는 것이 좋습니다!** webpack의 전체 개념은 더 많은 모듈식 프런트엔드 개발을 허용하는 것입니다. 이는 응집도가 높고 숨겨진 종속성(예: 전역 변수)에 의존하지 않는 격리 된 모듈을 작성하는 것을 의미합니다. 그러므로 필요한 경우에만 이 기능을 사용하세요.

_shimming_ 이 유용한 또 다른 경우는 더 많은 사용자를 지원하기 위해 브라우저 기능을 [폴리필](https://en.wikipedia.org/wiki/Polyfill_%28programming%29)하려는 경우입니다. 이 경우 패치가 필요한 브라우저에만 해당 폴리필을 제공할 수 있습니다. (예: 요청 시 로드)

해당 글에서는 이러한 두 가지 사용 사례를 모두 살펴봅니다.

T> 간단하게 시작하기 위해 이 가이드는 [시작하기](/guides/getting-started)의 예에서 시작합니다. 계속해서 진행하기에 앞서 설정에 익숙해져야 합니다.

## Shimming Globals

전역 변수 shimming의 첫 번째 사용 사례부터 시작하겠습니다. 시작하기 전에 프로젝트를 다시 한번 살펴보겠습니다.

**프로젝트**

```diff
webpack-demo
 ├── package.json
 ├── package-lock.json
 ├── webpack.config.js
 ├── /dist
 │   └── index.html
 ├── /src
 │   └── index.js
 └── /node_modules
```

우리가 사용했던 `lodash` 패키지를 기억하시나요? 데모 목적으로 애플리케이션에서 전역적으로 제공하고 싶다고 가정해 보겠습니다. 이를 위해 `ProvidePlugin`을 사용할 수 있습니다.

[`ProvidePlugin`](/plugins/provide-plugin)은 webpack을 통해 컴파일된 모든 모듈에서 패키지를 변수로 사용할 수 있게 해줍니다. 변수가 사용되는 것을 webpack에서 확인하면 최종 번들에 주어진 패키지를 포함합니다. `lodash`에 대한 `import`문을 제거하고 플러그인을 통해 제공해보겠습니다.

**src/index.js**

```diff
-import _ from 'lodash';
-
 function component() {
   const element = document.createElement('div');

-  // 이제 이 스크립트로 Lodash를 가져옵니다.
   element.innerHTML = _.join(['Hello', 'webpack'], ' ');

   return element;
 }

 document.body.appendChild(component());
```

**webpack.config.js**

```diff
 import path from "node:path";
 import { fileURLToPath } from 'url';
+import webpack from "webpack";



const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

 export default {
   entry: './src/index.js',
   output: {
     filename: 'main.js',
     path: path.resolve(__dirname, 'dist'),
   },
+  plugins: [
+    new webpack.ProvidePlugin({
+      _: 'lodash',
+    }),
+  ],
 };
```

여기서 우리가 실질적으로 한 것은 webpack에게 알려주는 것입니다.

> 변수 `_`의 인스턴스가 하나 이상 존재한다면 `lodash` 패키지를 포함하고 필요한 모듈에 제공합니다.

빌드를 실행해도 동일한 출력이 표시되어야 합니다.

```bash
$ npm run build

..

  ./node_modules/lodash/lodash.js 530 KiB [built] [code generated]

```

또한 `ProvidePlugin`에서 "배열 경로"(예: `[module, child, ...children?]`)를 구성하여 모듈의 일부분만 내보낼 수 있습니다. 호출될 때마다 `lodash`에서 `join` 메소드만 제공하고 싶다고 가정해 보겠습니다.

**src/index.js**

```diff
 function component() {
   const element = document.createElement('div');

-  element.innerHTML = _.join(['Hello', 'webpack'], ' ');
+  element.innerHTML = join(['Hello', 'webpack'], ' ');

   return element;
 }

 document.body.appendChild(component());
```

**webpack.config.js**

```diff
 import path from "node:path";
 import webpack from "webpack";
import { fileURLToPath } from 'url';

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

 export default {
   entry: './src/index.js',
   output: {
     filename: 'main.js',
     path: path.resolve(__dirname, 'dist'),
   },
   plugins: [
     new webpack.ProvidePlugin({
-      _: 'lodash',
+      join: ['lodash', 'join'],
     }),
   ],
 };
```

`lodash` 라이브러리의 나머지는 삭제되므로 [트리 쉐이킹](/guides/tree-shaking)이 잘 수행됩니다.

## Granular Shimming

일부 레거시 모듈은 `this`가 `window` 객체에 의존합니다. `index.js`를 업데이트해 보겠습니다.

```diff
+// Assume we are in the context of `window`
+this.alert("Hmmm, this probably isn't a great idea...");
+
 function component() {
   const element = document.createElement('div');

   element.innerHTML = join(['Hello', 'webpack'], ' ');

   return element;
 }

 document.body.appendChild(component());
```

이것은 모듈이 CommonJS 컨텍스트에서 실행될 때 문제가 됩니다. 모듈 자체의 `this`가 전역 객체가 아니라 `module.exports`이기 때문입니다. 전역 객체로 호출되는 함수로 모듈을 래핑하면 이를 해결할 수 있으며, 로더가 필요 없습니다. `NormalModule`의 `processResult` 훅은 플러그인에 로더가 생성한 것을 전달하고 대체물을 받으므로, webpack이 파싱하기 전에 파일 주위에 코드를 추가하는 것은 설정에 넣을 수 있을 만큼 짧은 플러그인으로 충분합니다.

webpack의 [add-imports 예제](https://github.com/webpack/webpack/tree/main/examples/add-imports)가 바로 그 플러그인입니다. 위의 래퍼, 파일이 직접 명시하지 않는 사이드 이펙트 import, 실제 바인딩을 처리합니다.

W> 래퍼는 스크립트 전용입니다. `import`와 `export`는 최상위 레벨에서만 나타날 수 있으므로 ES 모듈을 함수로 래핑하는 것은 구문 오류입니다. 또한 ES 모듈 자체의 `this`는 어쨌든 `undefined`이며 `module.exports`가 아닙니다.

T> 모듈이 단지 _읽기만_ 하는 이름은 소스를 건드리지 않고 모듈이 읽는 곳에 이름을 바인딩하는 [`ProvidePlugin`](/plugins/provide-plugin/)의 역할입니다.

## Global Exports

라이브러리가 사용자가 사용할 것으로 예상하는 전역 변수를 생성한다고 가정해 보겠습니다. 이를 증명하기 위해 작은 모듈을 추가할 수 있습니다.

**프로젝트**

```diff
  webpack-demo
  ├── package.json
  ├── package-lock.json
  ├── webpack.config.js
  ├── /dist
  ├── /src
  │   ├── index.js
+ │   ├── globals.js
  └── /node_modules
```

**src/globals.js**

```js
const file = "blah.txt";
const helpers = {
  test() {
    console.log("test something");
  },
  parse() {
    console.log("parse something");
  },
};
```

소스 코드에서 이러한 작업을 수행할 가능성은 낮지만, 위에 표시된 코드와 유사한 코드를 포함하는 오래된 라이브러리를 만날 수 있습니다. 아무것도 내보내지 않는 파일에는 export를 추가해야 하는데, 이는 파일의 반대편에서 동일한 훅을 사용합니다. webpack의 [add-exports 예제](https://github.com/webpack/webpack/tree/main/examples/add-exports)가 바로 그 플러그인입니다.

위의 `globals.js`에 대해 `module.exports = { file, parse: helpers.parse };`를 추가하면 `file`을 `file`로, `helpers.parse`를 `parse`로 내보냅니다. 엔트리 스크립트(예: `src/index.js`)에서 `const { file, parse } = require('./globals.js');`를 사용할 수 있으며 원활하게 작동합니다.

T> 추가할 형식은 파일 자체의 것이며, 두 가지는 동일하지 않습니다. `module.exports = …`는 스크립트를 스크립트 그대로 유지하며, 위의 `globals.js`가 원하는 것입니다. `export { … }`는 소스에서와 마찬가지로 파일을 ES 모듈로 만들어 해당 export가 분석되고 트리 쉐이킹될 수 있습니다. 파일이 허용하는 곳에서는 이를 선호하세요. 예제에서 두 가지를 나란히 보여줍니다.

## Loading Polyfills

지금까지 논의한 대부분은 레거시 패키지 처리와 관련이 있습니다. 두 번째 주제인 **폴리필로** 넘어가겠습니다.

폴리필을 로드하는 방법에는 여러 가지가 있습니다. 예를 들어 [`babel-polyfill`](https://babeljs.io/docs/en/babel-polyfill/)을 포함하려면 다음과 같이하면 됩니다.

```bash
npm install --save babel-polyfill
```

메인 번들에 포함되도록 `import` 합니다.

**src/index.js**

```diff
+import 'babel-polyfill';
+
 function component() {
   const element = document.createElement('div');

   element.innerHTML = join(['Hello', 'webpack'], ' ');

   // `window`의 컨텍스트에 있다고 가정합니다.
   this.alert("Hmmm, this probably isn't a great idea...");

   return element;
 }

 document.body.appendChild(component());
```

T> `import`한 것을 변수에 바인딩하지 않습니다. 이는 폴리필이 나머지 코드 베이스 이전에 자체적으로 실행되는 특정 기능이 존재한다고 가정하기 때문입니다.

이 접근 방식은 번들 크기보다 정확성을 우선시합니다. 안전과 견고함을 위해서는 폴리필이나 shim이 **다른 모든 코드보다 먼저** 실행되어야 하므로 동기식으로 로드하거나 모든 앱 코드는 모든 폴리필이나 shim이 로드된 후에 로드해야 합니다.
또한 커뮤니티에는 최신 브라우저에 폴리필이 "필요하지 않다"거나 폴리필이나 shim이 누락된 기능을 추가하는 역할만 한다는 오해가 많이 있습니다. 사실, 가장 최신 브라우저에서도 종종 _깨진 구현을 복구_ 합니다.
따라서 번들 크기 비용이 발생하더라도 모든 폴리필이나 shim을 무조건 동기식으로 로드하는 것이 모범 사례입니다.

문제가 해결됐다고 생각하고 위험을 감수하고 싶다면 다음과 같은 방법도 있습니다.
`import`를 새 파일로 이동하고 [`whatwg-fetch`](https://github.com/github/fetch) 폴리필을 추가해 보겠습니다.

```bash
npm install --save whatwg-fetch
```

**src/index.js**

```diff
-import 'babel-polyfill';
-
 function component() {
   const element = document.createElement('div');

   element.innerHTML = join(['Hello', 'webpack'], ' ');

   // `window`의 컨텍스트에 있다고 가정합니다.
   this.alert("Hmmm, this probably isn't a great idea...");

   return element;
 }

 document.body.appendChild(component());
```

**project**

```diff
  webpack-demo
  ├── package.json
  ├── package-lock.json
  ├── webpack.config.js
  ├── /dist
  ├── /src
  │   ├── index.js
  │   ├── globals.js
+ │   └── polyfills.js
  └── /node_modules
```

**src/polyfills.js**

```js

import "whatwg-fetch";
```

**webpack.config.js**

```diff

 import webpack from "webpack";
 import { fileURLToPath } from 'url';

 const __filename = fileURLToPath(import.meta.url);
 const __dirname = path.dirname(__filename);

 export default {
-  entry: './src/index.js',
+  entry: {
+    polyfills: './src/polyfills',
+    index: './src/index.js',
+  },
   output: {
-    filename: 'main.js',
+    filename: '[name].bundle.js',
     path: path.resolve(__dirname, 'dist'),
   },
   plugins: [
     new webpack.ProvidePlugin({
       join: ['lodash', 'join'],
     }),
   ],

```

이를 통해 새로운 `polyfills.bundle.js` 파일을 조건부로 로드하는 로직을 추가 할 수 있습니다. 이 결정을 내리는 방법은 지원 기술과 브라우저에 따라 다릅니다. polyfill이 필요한지 여부를 확인하기 위해 몇 가지 간단한 테스트를 수행합니다.

**dist/index.html**

```diff

   <head>
     <meta charset="utf-8" />
     <title>Getting Started</title>
+    <script>
+      const modernBrowser = 'fetch' in window && 'assign' in Object;
+
+      if (!modernBrowser) {
+        const scriptElement = document.createElement('script');
+
+        scriptElement.async = false;
+        scriptElement.src = '/polyfills.bundle.js';
+        document.head.appendChild(scriptElement);
+      }
+    </script>
   </head>
   <body>
-    <script src="main.js"></script>
+    <script src="index.bundle.js"></script>
   </body>
 </html>
```

이제 엔트리 스크립트에서 일부 데이터를 가져올 수 있습니다.

**src/index.js**

```diff

 document.body.appendChild(component());
+
+fetch('https://jsonplaceholder.typicode.com/users')

+  .then((json) => {
+    console.log(
+      "We retrieved some data! AND we're confident it will work on a variety of browser distributions."
```

빌드를 실행하면 `polyfills.bundle.js` 파일이 생성되고 브라우저에서 원활하게 동작하게 됩니다. 이 설정은 개선될 수 있지만 실제로 필요한 사용자에게만 폴리필을 제공하는 방법에 대한 좋은 아이디어입니다.

## Further Optimizations

`babel-preset-env` 패키지는 [browserslist](https://github.com/browserslist/browserslist)를 사용하여 브라우저 매트릭스에서 지원되지 않는 항목만 트랜스파일합니다. 이 사전 설정은 [`useBuiltIns`](https://babeljs.io/docs/en/babel-preset-env#usebuiltins) 옵션(기본값 `false`)과 함께 제공되며, 전역 `babel-polyfill`을 가져오는 것을 `import` 패턴을 통해 더 세분화 된 기능으로 변환할 수 있습니다.

{/* eslint-skip */}

```js
import "core-js/modules/es7.string.pad-start";
import "core-js/modules/es7.string.pad-end";
import "core-js/modules/web.timers";
import "core-js/modules/web.immediate";
import "core-js/modules/web.dom.iterable";
```

자세한 내용은 [babel-preset-env 문서](https://babeljs.io/docs/en/babel-preset-env)를 참고하세요.

### Serving a smaller polyfill to modern browsers

동일한 폴리필 세트를 두 번 컴파일하고 런타임에 적합한 것을 선택하여, 필요가 적은 브라우저는 조금만 다운로드할 수 있습니다. 엔트리가 어떤 빌드를 가져올지 결정하며, 두 빌드 모두 애플리케이션 이전에 로드됩니다.

**src/index.js**

{/* eslint-skip */}

```js
(async () => {
  if (isLegacyBrowser()) {
    await import("./polyfills?legacy");
  } else {
    await import(/* webpackMode: "eager" */ "./polyfills");
  }
  await import(/* webpackMode: "eager" */ "./app");
})();
```

**src/polyfills.js**

{/* eslint-skip */}

```js
import "core-js";
import "regenerator-runtime/runtime";
```

두 빌드의 차이는 Babel에게 지정하는 타겟뿐이며, 이는 [`Rule.resourceQuery`](/configuration/module/#ruleresourcequery)가 `?legacy` 쿼리를 통해 선택합니다.

**webpack.config.js**

```js
export default {
  module: {
    rules: [
      {
        test: /\.js$/,
        include: [path.resolve(__dirname, "src")],
        oneOf: [
          {
            resourceQuery: /legacy/,
            loader: "babel-loader",
            options: {
              presets: [
                [
                  "@babel/preset-env",
                  { useBuiltIns: "entry", targets: "ie 11" },
                ],
              ],
            },
          },
          {
            loader: "babel-loader",
            options: {
              presets: [
                [
                  "@babel/preset-env",
                  { useBuiltIns: "entry", targets: "last 2 versions" },
                ],
              ],
            },
          },
        ],
      },
    ],
  },
};
```

W> 이것이 위 섹션에서 경고한 트레이드오프입니다. 폴리필이 이제 비동기적으로 로드되므로 엔트리 외부의 어떤 것도 폴리필 이전에 실행될 수 없습니다. 그래서 애플리케이션 자체가 엔트리의 일부가 아닌 import로 가져오는 것입니다. `isLegacyBrowser()`도 폴리필 이전에 실행되므로 가장 오래된 타겟이 파싱할 수 있는 구문으로 작성해야 합니다.

### Two bundles from one source with layers

위의 `?legacy` 쿼리는 import를 하나씩 태그합니다. 대신 [layer](/configuration/entry-context/#entry-descriptor)는 전체 엔트리를 태그합니다. webpack은 레이어당 한 번씩 엔트리의 그래프를 탐색하므로 도달하는 모든 파일이 두 개의 별도 모듈로 두 번 존재하며, [`Rule.issuerLayer`](/configuration/module/#ruleissuerlayer)가 각 복사본에 대한 로더를 선택합니다. 폴리필은 레거시 엔트리에만 포함되며, 페이지에서 브라우저 감지가 실행되지 않습니다.

**webpack.config.js**

```js
import path from "node:path";

const src = path.resolve(process.cwd(), "src");

const babel = (targets, corejs) => ({
  loader: "babel-loader",
  options: {
    presets: [
      [
        "@babel/preset-env",
        {
          targets,
          useBuiltIns: corejs ? "usage" : false,
          corejs,
        },
      ],
    ],
  },
});

export default {
  entry: {
    modern: { import: "./src/index.js", layer: "modern" },
    legacy: { import: "./src/index.js", layer: "legacy" },
  },
  output: {
    filename: "[name].js",
    path: path.resolve(process.cwd(), "dist"),
    environment: {
      arrowFunction: false,
      const: false,
      destructuring: false,
      dynamicImport: false,
      forOf: false,
      module: false,
      optionalChaining: false,
      templateLiteral: false,
    },
  },
  module: {
    rules: [
      {
        test: /\.js$/,
        include: src,
        issuerLayer: "modern",
        use: babel("last 2 chrome versions, last 2 firefox versions", false),
      },
      {
        test: /\.js$/,
        include: src,
        issuerLayer: "legacy",
        use: babel("ie 11", 3),
      },
    ],
  },
};
```

엔트리의 `layer`는 엔트리 모듈 자체에 대해 `issuerLayer`가 일치하는 것이며, 엔트리가 import하는 모든 모듈이 이를 상속하므로 레이어당 하나의 규칙으로 전체 그래프를 커버합니다. 하나의 컴파일이 두 번들을 모두 내보내며, 페이지에서 브라우저가 선택하도록 합니다. `type="module"`을 이해하는 브라우저는 `nomodule`을 무시하고, 이해하지 못하는 브라우저는 module script를 무시합니다.

```html
<script type="module" src="/modern.js"></script>
<script nomodule defer src="/legacy.js"></script>
```

T> webpack 5.102.0 이전에는 `experiments.layers: true`로 레이어를 활성화해야 했습니다.

W> [`output.environment`](/configuration/output/#outputenvironment)는 엔트리가 아닌 컴파일에 속하므로, 두 번들이 하나의 런타임을 공유합니다 — 위에서처럼 지원하는 가장 오래된 브라우저에 맞게 설정하세요. 이는 **webpack이 생성하는** 코드를 제한하며, 자체 소스를 트랜스파일하지 않습니다. 그것은 레이어별 `babel-loader`의 역할입니다.

### Two configurations, when the modern build has to be ESM

레이어는 출력 형식을 다르게 설정할 수 없습니다. `output.module`은 `output.environment`와 같은 이유로 컴파일 전체에 적용되기 때문입니다. 모던 빌드가 실제 ECMAScript 모듈이어야 하는 경우 — `export` 구문, 청크 로딩을 위한 `import()` — 설정 배열을 전달하고 각각이 자체 컴파일이 되도록 하세요.

```js
import path from "node:path";

const common = {
  mode: "production",
  entry: { app: "./src/index.js" },
};

export default [
  {
    ...common,
    name: "modern",
    output: {
      path: path.resolve(process.cwd(), "dist/modern"),
      filename: "[name].mjs",
      chunkFilename: "[name].chunk.mjs",
      module: true,
      chunkFormat: "module",
      chunkLoading: "import",
      library: { type: "module" },
    },
  },
  {
    ...common,
    name: "legacy",
    output: {
      path: path.resolve(process.cwd(), "dist/legacy"),
      filename: "[name].js",
      chunkFilename: "[name].chunk.js",
      library: { type: "var", name: "App" },
      environment: {
        arrowFunction: false,
        const: false,
        destructuring: false,
        dynamicImport: false,
        forOf: false,
        module: false,
        optionalChaining: false,
        templateLiteral: false,
      },
    },
  },
];
```

모던 컴파일은 `export`를 내보내고 `import()`로 청크를 로드합니다. 레거시 컴파일은 `var` 라이브러리를 내보내고 `environment.dynamicImport`가 `false`이기 때문에 주입된 `<script>`로 청크를 로드합니다. 각 설정의 `module.rules`에 타겟별 `babel-loader` 규칙을 평소처럼 추가하세요 — 두 개의 컴파일로는 `issuerLayer`가 구분할 것이 없으므로 레이어가 필요하지 않습니다.

## Node Built-Ins

`global`, `__dirname`, `__filename` 같은 Node 내장 기능은 특별한 로더나 플러그인을 사용하지 않고도 [`node`](/configuration/node) 옵션으로 설정 파일에서 직접 처리할 수 있습니다. `process`와 `buffer` 같은 Node 핵심 모듈은 webpack 5에서 폴리필되지 않습니다. [`ProvidePlugin`](/plugins/provide-plugin/)이나 [`resolve.fallback`](/configuration/resolve/#resolvefallback)으로 제공하세요. 자세한 내용과 예제는 [node 설정 페이지](/configuration/node)를 참고하세요.

## Other Utilities

레거시 모듈을 다룰 때 도움이 될 수 있는 몇 가지 도구가 있습니다.

모듈의 AMD/CommonJS 버전이 없고 `dist`를 포함시키려는 경우, `/configuration/module/#modulenoparse`에 해당 모듈을 `noParse`로 지정할 수 있습니다. 이렇게 하면 webpack은 모듈을 파싱하거나 `import` 및 `require()` 문을 해석하지 않고 포함합니다. 이 방법은 빌드 성능을 향상시키는 데에도 사용됩니다.

W> `ProvidePlugin`과 같이 AST가 필요한 기능은 동작하지 않습니다.

마지막으로 AMD, CommonJS, 레거시의 조합과 같이 여러 [모듈 스타일](/concepts/modules)을 지원하는 모듈이 있습니다. 이러한 경우의 대부분은 먼저 `define`을 확인한 후 약간 특이한 코드를 사용하여 속성을 내보냅니다. 이런 경우 [Granular Shimming](#granular-shimming)에서 사용한 동일한 [add-imports 예제](https://github.com/webpack/webpack/tree/main/examples/add-imports) 플러그인으로 해당 파일에 `var define = false;`를 앞에 추가하여 CommonJS 경로를 강제하는 것이 도움이 될 수 있습니다.
